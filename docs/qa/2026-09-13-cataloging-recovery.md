# 保留候选修正再次停止：原因与回归

2026-09-13 的实际 DeepSeek API 记录显示：模型已补交场景和角色状态，随后调用 `save_external_cataloging_candidates(candidates=[], finalize=true)`。旧候选中的 `action`、`item_type`、`operation` 等重复内部字段被当前 Schema 拒绝。该工具却返回 `status=ok`，顶层缺项包含错误、恢复上下文的缺项为空。模型将阻塞错误理解为旧版警告，以文字宣布完成；原生循环随即停止，且没有将最后的文字回复保存到章节执行记录。

## 当前行为

- 数据迁移 `300a38_candidate_envelope` 只清理与候选类型、操作、目标 ID 列完全一致的冗余封装字段。正文、人物资料、候选 ID、状态、作者编辑和确认保留；冲突值和未知业务字段不猜测、不转换。
- `plan_validation.inspect_complete_plan` 是提交、恢复和写入前校验的共同来源。所有无效的既有候选都会返回候选 ID、类型、字段位置和原因；作者保护内容明确标为需要作者处理。
- 显式 `finalize` 未成功时返回错误。顶层与恢复上下文的错误、缺项相同；已暂存部分候选不代表本章已经完成。
- 原生 API 模型仅回复文字时，保存该回复，再把具体阻塞项交回同一模型对话。最多允许两次这种继续修正机会，第三次仍未继续调用工具便暂停，并保留具体原因。
- 模型明确提供的正确空数组或 `null` 可以修正旧字段的错误类型；有效的既有丰富内容仍按原有合并规则保留，作者编辑保护不变。
- API、CLI/MCP 使用同一校验回执和共享提示词；Android 的提示词投影已重新生成。

## 验证

新增回归先在旧代码上复现了四个失败分支，再验证失败回执、逐候选诊断、作者保护、同轮继续、有限重试、迁移幂等以及候选 ID 保留。

后端全量回归 2822 项通过、5 项跳过；Android `testDebugUnitTest` 与 `compileDebugKotlin` 检查通过。

实际失败任务中与校验有关的 75 行数据以只读方式投影到内存数据库，复现了 9 个既有候选错误。重复字段迁移后，按记录中模型已经选择的绑定 ID 提交明确的工具修正样例，计划成功进入待确认状态。没有写入用户数据库、没有生成完整数据库副本、没有请求真实模型；该回放验证协议和状态转换，不代表已经测得真实模型修正成功率。

复核日志保存在 `.build/cataloging-recovery-*.log`；测试入口为 `backend/tests/test_cataloging_plan_recovery.py`。架构检查通过，模块依赖无循环。构建后的安装包单独保存，避免覆盖先前交付的测试包。
