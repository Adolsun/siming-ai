# 旧 MCP 重连导致数据库备份持续增长

## 现场证据

2026-09-12 对用户数据目录进行文件大小统计：`backups` 约 107.258 GiB，其中 `pre-332` 备份及其辅助文件约 92.698 GiB；调用记录库 `diagnostics/context-traces.sqlite3` 为 53,248 字节。检查期间曾观察到新增 `pre-332` 完整备份，单份约 470 MB。

仅查询数据库版本字段，正式库和最近的 `pre-332` 备份均为 `300a36_outline_projection_identity`，应用版本元数据为 3.3.16。Codex、OpenCode、Claude 的用户级 `siming` MCP 配置却仍指向 `D:\AI\agent` 的 Python 入口，该源码版本为 3.3.2。

旧启动逻辑在检查 Alembic 是否认识当前数据库版本之前创建全库备份，随后升级失败。每次客户端重连都会复制新的一份。当前分支也保留了这一顺序问题；另外，多个 MCP 进程能同时读取旧版本，各自备份并运行迁移。

## 修复

- 当前唯一的 `bootstrap_database` 路径先校验完整迁移链。遇到未知版本、较新的数据库或不能到达当前 head 的退役版本时，直接进入只读恢复并提示更新应用及 MCP 命令，不备份、不重写版本标记。
- SQLite 启动使用已有跨进程文件锁机制。获取启动锁后重新读取版本，第一进程完成迁移后，其余进程检查当前版本，不再重复复制或迁移。启动锁和事务写锁分开，避免迁移内部的写事务等待自身。
- 合法迁移仍使用 SQLite 在线备份并做完整性检查；迁移失败仍保留并返回已验证的恢复备份。
- 本机三个客户端仅替换 `siming` 的命令与参数为已安装的 `D:\Siming\Siming.exe --mcp-server --permission-pack auto`。逐个保留原配置，解析比较确认其他服务、权限与设置不变。已运行客户端需重新加载 MCP 配置；没有改动旧源码目录。

Android 本机业务数据库使用 Room 迁移，没有这里的 Alembic 启动复制路径，故本次没有修改 Android。Android 连接 Gateway 时，服务端使用相同的后端启动保护。API 路由、工具参数、权限及小说业务状态契约未改变。

## 验证与交付边界

- 修改前的 4 个复现案例全部失败：未知版本、已知但更高的版本、退役标记对应更高版本、三个进程并发迁移。
- 修复后 6 个相关测试文件共 47 项通过，包含真实 stdio MCP 子进程对未知数据库连续重连三次，以及三个独立进程只生成一份迁移备份。正常升级、WAL 备份完整性、事务写锁、MCP 入口与运行时迁移回归通过。
- 已安装 3.3.16 MCP 在 D 盘合成数据目录完成 `initialize` 握手，无模型调用。
- Ruff 检查与格式检查通过；后端架构检查 672 个模块、循环依赖 0、错误 0。
- 证据日志：`.build/backup-storage-repro.log`、`.build/backup-storage-regression.log`、`.build/backup-storage-architecture.log`。

没有删除历史数据库备份，没有通过迁移或工具写入用户小说数据。已有约 107 GiB 备份不会因修复自动腾空，也不能据此推断先前全部磁盘占用均来自该目录。这里未新增通用备份自动删除策略。

这次代码保护是在上一份 3.3.17 测试包之后完成的，旧安装包不包含它。本轮只完成源码修复与本机 MCP 配置纠正，未重新打包、安装或发布。配置指向当前安装位置，后续覆盖安装时会使用该位置的新版本。
