# 立项写入成功后总结失败：回执容量修复

## 复现与根因

针对 3.3.16 源码定位到一次本机已结束的立项回合。实际模型为 `deepseek:deepseek-flash`，`patch_creation_entity` 已成功提交一次修改，审计回执为 `status=ok`、`write_committed=true`。随后两次总结都返回 DSML，最终显示“修改已保存，但模型未能生成有效总结”。

该工具的完整返回中，`data.artifact` 是包含整个阶段正文的对象。通用 `status_only` 契约把 `artifact` 当成普通标识字段，直接复制了整个对象。此回合的模型可见结果达到 8,601 字节，超过声明的 4,096 字节上限，被替换成 `tool_result_over_capacity` 错误。于是执行审计记录成功，模型却收到失败，仍然尝试读取或重做修改；关闭工具后的总结请求将这些调用以 DSML 正文返回。

## 当前实现

- 中央工具结果契约支持声明嵌套对象的可见元数据。立项写工具共用一个回执契约：保留实际状态、实体 ID、实体名、阶段、revision 等字段，不将实体正文和完整阶段正文附带到写入回执中。
- `artifact` 是字符串时保留字符串；是完整对象时仅投影其声明的元数据。完整返回仍保存在原有业务和审计路径，读取工具继续负责读取正文。
- Native Agent 和 CLI/MCP 继续使用同一中央投影器。原生调用与工具结果仍完整配对，总结继续使用原有的无工具路径；输出校验和一次成功写入边界保持有效。
- Android 从 PC 注册表导出相同的字段、嵌套对象规则和容量上限，移除独立维护的旧写入字段列表。手机本地实体结构中的 ID 与实体名也会进入回执。

## 验证

1. 后端真实内存数据库回归：读取含大段背景的角色、改名、提交、总结。修复前会得到用户报告的失败提示；修复后总结收到成功结果和新 revision，写入仅一次，背景保持完整，回合没有悬挂工具事务。
2. 共享 JSON fixtures 验证嵌套阶段对象、字符串阶段标识、手机扁平实体结构，PC 与 Android 对同一输入产生相同的元数据。大正文超过 4 KiB 时仍能得到完整有效的小回执，输入原文没有被修改。
3. 后端主要回归 204 项通过；补充 MCP、注册表及最终契约检查的一组 126 项通过（两组包含重叠用例）。覆盖读写边界、失败重试、总结校验、立项运行记录、MCP 结果和移动端生成契约。
4. Android 立项相关 41 项测试与 `lintDebug` 通过。新增独立 HTTP/SSE 回归完成真实本地角色改名、一次持久化和总结，确认正文保留且不依赖 PC 运行。
5. 后端架构、Prompt、Ruff、导入边界检查通过；手机/PC 27 项能力契约检查通过。

使用本机已有配置，对同一 DeepSeek API 进行了收尾请求对照：原错误回执复现 DSML；由修复后的中央投影器生成的回执为 376 字节、`status=ok`，模型正常说明了实际完成的修改，没有返回 DSML 或原生工具调用。本次对照只生成回复，没有执行任何业务工具，也没有重新修改实际立项资料。
