# 2026-09-07：新章规划循环、工具回执与大纲数量契约修复

本轮修复已在真实配置的模型上走通“开始写新章节 → 查找真实位置 → 选择上下文 → 生成待确认大纲草稿”。最终生成 3 个章级节点，锚定在既有第 41 章之后、原卷之下，并结束 Agent 回合；没有确认草稿或写入正式章节、大纲、角色及世界观数据。

## 复现与根因

1. 原问题运行在第 59 个模型步骤时已累计 96 个工具步骤，反复读取大纲、章节和同一任务上下文，没有进入大纲生成器。用户提供的运行文本也出现了对早期结果不可见的描述。
2. 运行时把一次成功读取过的原生工具事务立即移出当前模型上下文，换成简短回执。这只能证明“执行过”，不能代替继续规划需要的原始 ID、正文、分页信息和上下文令牌。
3. `prepare_task_context` 的成功状态为 `ready`，旧回执逻辑没有识别它，错误地显示“执行失败”。
4. 修复结果保留后，真实复测进一步发现大纲生成器提示词要求单章额外输出场景节点，而保存校验要求总数严格等于 `batch_count`。一次真实调用要求 1 个节点，模型按提示提交了 4 个，被校验拒绝；通用错误清洗又遮蔽了数量冲突的原因。

## 当前实现

- 当前用户回合内的完整工具事务持续保留，包括已经消费过的批次、原生调用、模型返回的思考内容和提供商状态。只有回合关闭后才能归档成回执。历史 checkpoint 继续负责已关闭历史，不代替当前回合事实。
- 完整请求仍统一计数，输出额度和安全余量照常预留；容量不足时明确拒绝，不删除当前结果后冒充上下文完整。未知模型的 256K 兜底与已配置档案优先级未改变。
- PC、手机独立运行及立项助手采用同一结果生命周期。`ready` 显示“已就绪”，等待确认、取消和跳过不再被当成执行失败；前端日志与历史回执也区分这些状态。
- 给模型的工具说明要求复用本轮已知 ID，并按节点或相关分支查询，避免仅为定位一个章节遍历整棵树。没有加入正则或关键词意图路由。
- 大纲规划提示词与保存契约统一：按审阅上下文的精确数量提出节点，场景细节写入章纲的 `summary`。生成器的 `nodes.minItems/maxItems` 同时绑定本次数量。建档模块的场景拆分、重建与粒度规则保持不变。
- 大纲数量不符返回 `outline_node_count_mismatch`、`expected_count` 和 `actual_count`，API、CLI/MCP 的安全投递仍能保留这些确定性信息，不反射任意异常文本。手机端同步数量约束，移除了与统一上限不一致的独立 8 节点限制。
- 没有新章节大纲时仍先生成待确认大纲。不会跳过规划直接写正文，不会自动确认、保存或建档，不会同轮自动续写。

失败尝试保留在本地证据中：首次到达生成器后失败；独立重放生成调用返回 3 节点，但不等于整条流程通过。第二次顺序扫描完整大纲树，触发测试脚本的 24 次调用上限。第三次捕获上述提示词与数量校验冲突，未生成草稿。最终测试脚本允许最多 64 次调用，实际用了 21 次；未修改应用的运行终止策略。
