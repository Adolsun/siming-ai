## 实际故障

只读检查安装后的数据库，定位回合 `22798c24-d308-4fb7-a8c7-77f5338d0c6f`，模型为 `deepseek:deepseek-v4-flash`，使用 API 原生工具流程。14:12:54 开始，最终在 14:35:53 取消，结束时为第 65 轮。首次捕获的是前 93 条步骤记录，不能将该快照当作整个回合的最终调用总数。

- `get_project_info` 返回 37,131 字节，超过该工具的 16,384 字节契约，其中包含整份立项资料。查询本身成功，模型却只收到投递拒绝；旧记录还将原始执行成功呈现为成功，界面另显示含糊的“无法安全投递”。
- 快照中三次 `search_outline` 报错分别请求了 200、200、150 字摘要，被旧 schema 的 100 字上限拒绝。这与模型的总上下文不足是两回事。
- 原生 API 已返回思考增量，但工作区执行器只保留了供应商续接数据，没有将可见增量发到界面。前端另有逐字慢放，可能使长思考显示明显落后于接收。

此前仅验证小型项目与批次准入，遗漏了真实长立项文档和读取参数的可用性，这是上一轮覆盖不足。

## 当前读取契约

以下数字是单页工程策略，不是小说、章节或大纲的总字数限制。模型请求超过安全单页长度时，服务端正常返回安全页、实际范围与续读位置，不再只因为请求较长文本而触发原来的小字数 schema 错误。输入整数仍受协议类型与范围校验。

| 工具 | 当前行为 | 完整性与余量 |
| --- | --- | --- |
| `get_project_info` | 设置概览不夹带立项长文；长字段有明确预览标记，单字段最多返回 2,000 字符 | 原字段未修改；按 `field_ranges` 读取；结果仍受 16 KiB 契约约束 |
| `get_project_creation_brief` | 立项 JSON 文档按最多 2,000 字符分页，也可用 JSON Pointer 读取指定字段 | 提供总长度、偏移和文档哈希；未读完的 JSON 文本切片不能视为完整文档 |
| `search_outline` | 默认每个摘要字段 500 字符，安全页最多 1,000 字符 | 摘要可持续读取，预算随单页长度、条目数及返回字段数变化 |
| `search_chapters` | 默认每章 2,000 字符，安全页最多 4,000 字符 | 可直接按真实 `chapter_id` 读取；每章 `next_arguments` 固定该 ID，避免同名与列表顺序变化导致读错 |

当前项目有 207 个大纲节点，443 段非空摘要：中位数 160、95 分位 331、最长 427 字。100 字能一次读完 64 段，500 字能覆盖这批全部摘要。这只是默认值在一个项目中的证据，不是全体用户的长度分布，也不能据此限制长正文。

容量核算先扣除绑定模型的输出预留与安全余量；再按完整工具消息、供应商续接状态、参数及声明结果预算进行整批准入。字符页按每个 Unicode 字符最多 6 字节的 JSON 编码开销计费，另计算结构字段与工具消息中的再次转义。准备阶段的默认结果预留不是另一个固定批次上限。容量不足时不执行半批，不截断后伪装为完整结果，不吞掉已有模型状态。

边界测试确认：当一批读取恰好用完可用输入增长预算时，仍保留独立的 4,000 Token 输出空间和 512 Token 安全余量；再少 1 Token 就在执行前拒绝。这里的 4,000/512 是该测试绑定的档案值，不是对全部用户强制设置的值。日志记录输出预留、安全余量、封装开销和批次之后的剩余量，不写入正文或密钥。

## 投递与思考显示

投递失败时，持久记录同时保留原始执行结果和结构化的 `model_delivery` 失败。界面可以区分“工具已执行”与“模型未收到结果”，显示实际字节与契约上限；不会把投递失败变成重放已完成写入的理由。

只展示模型 API 明确返回的可见思考文本，供应商不透明状态仍不公开。增量随接收展示，移除逐字慢放；供应商最终文本修正可以替换流中版本，正常完成的内容可从持久对话记录恢复。没有返回可见思考的模型或 CLI 不会被伪造一段“思考”。

前端回归另外发现立项资料编辑器的自动保存问题：失败后保存状态变化会重新安排 5 秒定时器，反复发起保存并清除错误提示。当前改为失败后保留未保存内容与错误，作者点击“重试保存”或继续编辑后才再保存；读取失败不会显示无效的保存重试按钮。手机端此处原本采用明确的“保存修改”操作，没有 PC 的 5 秒定时器；业务写入契约不变。

## 验证边界

- 手机端独立执行的共同读取能力遵循相同参数与分页语义，字符偏移按 Unicode 字符计算；不依赖 PC 界面。手机端现有工具目录未提供正式作品的 `get_project_creation_brief`，本轮没有擅自开放或假称已实现该能力。
- CLI/MCP 使用同一读取工具契约；完整会话的上下文由对应 CLI 管理，不能用 API 侧预算证明外部 CLI 的内部预算完全相同。
- 分页不会赋予模型无限上下文。一次长文改写仍受绑定模型的输入和输出容量约束；本轮长文本读取通过不等于所有模型都能一次生成或改写 5 万字。
- 真实模型测试仍有一次冗余读取。长时间运行时的查询效率、活动回合体积与并发修改后的读取一致性仍应继续观察，不能拿一个只读夹具证明所有创作流程已经验收。
- 本轮没有完成新的十万字、四十章以上创作与逐章建档验收，也没有将合成夹具冒充司命生成并导出的小说项目。
