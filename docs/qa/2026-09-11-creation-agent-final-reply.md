# 立项 Agent 收尾回复验收

本轮修复 DeepSeek API / deepseek-flash 在立项写入后把 DSML 工具协议作为正文输出的问题。基于 3.3.15 已同步的 develop，未修改版本号、API 地址、模型发现或业务工具参数。

## 复现与根因

以本地 SQLite 和模拟模型响应执行类别选择、真实快照读取、真实 patch_creation_session 写入，再让模型返回原始 DSML。修复前数据库 revision 已增加一次，但 DSML 被接受为最终回复；若同一收尾步骤返回原生函数调用，则因工具已经关闭而直接抛错。

原因是工具关闭后仍执行原规划步骤，没有进入已有的显式总结流程。Android 独立模式也有该分支，并会在输出校验前发送模型正文片段。

## 当前权威路径

- 达到一次成功写入或三次失败写入边界后，立即结束工具阶段，统一进入总结步骤。总结保留最新作者消息和真实工具回执，通过服务端运行指令限定当前只需说明结果。
- 总结不开放工具。DSML 命名空间标记、截断的 DSML 标记、空总结及未授权的原生函数调用均不能成为最终回复。只做输出协议校验，不把正文解析成可执行调用，也不从作者自然语言推断工具或目标。
- 总结最多生成两次，即首次输出不合格时纠正一次。纠正使用相同的已完成操作回执，始终关闭工具，不重放读取或写入。请求失败直接结束总结生成。
- 总结最终仍不可用时，明确说明总结失败，并显示可验证的执行结果。已保存的修改保留；已启动的任务仅报告已启动；未写入时明确说明没有保存。终态回执关闭完整工具事务，避免留下已经结束回合的待消费事务。
- PC 的运行快照和回合 outcome 记录 reply_status、reply_diagnostics；Android 的会话审计同步记录这两项。无效总结不作为最终消息保存，不注入后续总结请求。
- Android 通过构建导出复用 PC 的收尾提示、协议检测模式和尝试上限。回复校验完成后才发送 reply_delta，与 PC 的显示时机一致。CLI/MCP 继续按已验证回执收尾，不追加一次可能重放业务的 CLI 调用。

## 验证

后端相关 117 项测试通过，覆盖立项执行、回合持久化、检查点、原生工具协议、DeepSeek 适配器和生成的手机契约。新增用例验证：

- 一次真实写入后直接进入显式总结，revision 只增加一次。
- 完整、混合正文、单/双竖线、ASCII 竖线、HTML 转义及截断 DSML 的拦截和纠正。
- 总结返回原生写工具时不执行；连续异常和请求失败时保留写入，并结束回合。
- 正式作品创建成功后使用确定性回执，不额外请求模型；已启动任务不被描述为已经完成。
- DeepSeek SDK 的分片正文在收集后交给输出校验，工具关闭时请求不携带 tools 或 tool_choice，模型 ID 保持 deepseek-flash。

Android 立项与相关界面 39 项测试、lintDebug 通过。覆盖独立 HTTP/SSE 调用、只写入一次、三次失败后停止、总结纠正上限、请求失败恢复、原始输出不提前显示，以及诊断字段的审计保存。

后端架构、Prompt、Ruff 和导入边界检查通过；手机/PC 的 27 项能力契约检查通过。

测试全部使用内存数据库、模拟 SDK 或本地 MockWebServer，没有调用作者的 DeepSeek API，也没有改动作者的实际立项数据。

Android APK 签名、应用 ID、版本及 ZIP 完整性校验通过；包内共享回复契约与源文件字节一致，编译产物包含本次回复校验逻辑。两端 SHA256 和文件大小记录在同目录 `package-manifest.json`，各安装文件旁也附有校验文件。
