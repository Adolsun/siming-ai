# 写下一章时工具名错误的诊断与恢复

## 实际证据

2026-09-13 17:13，作品助手收到“继续写下一章”后以 `conversation_protocol_invalid` 结束。
只读检查本地调用记录得到：

- 17:08 成功任务的 trace 为 `8f012945e257484889c2da21525cb640`。
  模型在选择 `story_knowledge`、`writing_context` 后调用 `list_chapters`、`search_outline_tree`，最终生成未保存章节草稿。
- 17:13 失败任务的 trace 为 `b4b945a5b3cc4c46b7bec0f4233df386`。
  模型同样先选择类别，但下一步返回 `list_chapters({"limit":10})` 和 `list_outline_tree({"root_id":""})`。
- 两次都是 DeepSeek API `deepseek-flash`。失败任务的 provider request #338 中，45 项实际开放工具包含
  `search_outline_tree`，没有 `list_outline_tree`；发送的 messages 中也没有这个错误名称。
  原始 provider response #356 和适配器输出 #360 都含有模型返回的错误名称。
- 持久错误为 `native_tool_not_open`，`call_index=1`，`iteration=2`。
  旧实现直接抛出终止异常，因此这个批次没有执行任何查询或写入；此前成功的类别选择已保留。

这次故障发生在查询工具选择阶段，尚未进入写章或建档。模型返回了未提供的工具名，运行时又缺少对这种错误的有限恢复处理。

## 当前处理契约

1. 仍然先完整校验 call ID、JSON 参数、类别控制器和终止工具的独占要求。
   缺失/重复 ID、非法 JSON、混合类别切换或混合草稿生成等不进入名称恢复。
2. 仅当批次结构有效、但含本步骤未开放的工具时，给整批调用逐一返回 `error` 回执。
   每份回执声明 `executed=false`，列出不可用工具和本步骤实际工具清单。
   不执行正确前缀，不映射工具别名，不改变参数，不自动开放类别。
3. 原始调用 ID、参数字符串、reasoning content 和 provider state 完整进入配对的原生事务；
   拒绝原因及调用记录先持久化，再交回同一模型。下一步仍走当前上下文预算和工具类别路径。
4. 恢复必须满足实际完整事务的预算。本轮第三次发生名称拒绝即停止，即最多两次修正机会；
   中途成功读取或类别切换不会重置次数。
5. 名称拒绝作为控制记录保存，不计作实际业务写入。日志中的整批拒绝步骤不能单独重放。
   最终错误及重新加载后的消息均保留具体工具名与修正次数，避免只显示泛化的协议失败。
6. 手机独立 Agent 使用相同错误回执、次数与预算边界，在手机会话存储中保存完整拒绝事务。
   PC 和手机共用事件回放夹具。既有工具授权、目标归属和草稿终止规则保持在原执行路径中校验。

本次处理针对作品助手原生工具名称拒绝，不会保证模型每次都输出正确结构；结构损坏、预算不足或修正次数耗尽仍会明确停止。
