# 建档后的角色刷新与大纲人物关联

## 现场核对

2026-09-12 对本机《笔下的名字》第一章的建档记录、角色数据库和 HTTP 角色接口进行只读核对：

- 沈墨、陆文昭、周砚、沈砚实际均为 v3，各有稳定档案、剧情状态两次版本记录。
- 当前目标、心理状态、位置、生死状态，以及声线、行为习惯、创伤触发等写作约束已有写入。
- 本轮基础资料主要补充别名；模型未提交背景、性格、能力的新内容，因此这些字段没有改写。已有字段的写入能力由新增回归覆盖，不以强行改变所有字段表示“更新成功”。
- 第一章有四条章节人物关联，但章纲和三个场景没有正式大纲人物关联。

## 原因与修复

1. 角色页面被工作区缓存，后台建档结束未发出页面刷新信号。新增工作区级建档刷新组件，复用任务查询，按实际进度和结束状态刷新缓存页面，聊天面板关闭时同样生效。未保存编辑与迟到响应通过表单修订号保护。
2. 建档输出中的描述性 `characters` 没有对应到旧写入字段，原立项落库也没有创建人物关联。当前契约统一使用显式 `character_ids`：模型从真实目录选择 ID，应用验证其存在及作品／会话归属，不从姓名或自由文本猜测绑定对象。
3. 同轮新角色可提供未使用的规范 UUID 作为 `client_id`，先创建角色，再应用引用该 ID 的大纲。章节人物清单同时投影到已确定的章纲。场景关联按当前版本替换，完成检查核对实际持久化的关联；缺失或越界关联不能算作完整建档。
4. 同步更新 API、MCP、CLI 所用权威候选工具定义、提示词和校验。已停用 `related_characters`，没有保留旧字段写入分支。
5. 立项提供 `character_index`，章节、场景保存和确认均验证角色 ID；建书时把立项实体 ID 映射为正式角色 ID。将建书数据组装移到独立模块，保持唯一调用实现。

旧数据中缺少的关联不会因安装代码自动推断补齐。缺少新必填字段的待保存立项细纲需由模型读取当前目录、补全 ID 后重新提交；校验失败保留原数据。

## 手机端

独立立项使用同样的角色目录、显式引用和写入校验，正式建书保留关联；转入 PC 时按传输目录映射 ID。角色目录 ID 与会话及记录内容关联，重排不改变引用；内容修改后返回新的真实实体回执，并按现有阶段机制使下游失效。

现有移动端建档通过 Gateway 执行同一后端建档契约；本次验证包括该共享契约和移动端独立立项，不把它描述为已实现手机独立建档。
