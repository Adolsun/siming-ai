# 首版卷纲生成与保存状态回执修复

## 运行记录与复现

本机安装程序的哈希确认其已包含此前的势力生成修复。此次卷纲任务的前两次调用带有 `entity_type: "volume"`，两次运行均以“全书主线与卷纲缺少 story_overview、core_conflict、ending_direction”结束。这是生成结果校验失败，不是工具参数 Schema 拒绝。

当时 `macro_outline` 为 `pending` 且 `data=null`。原实体合并逻辑从空阶段基线开始，只合并 `volumes`，丢弃模型返回的阶段顶层字段；即使模型提供了完整主线，保存前校验仍会失败。新增数据库回归已在修复前复现这一问题。

第三次调用不带 `entity_type`，实际已生成并保存 5 卷，revision 从 28 增至 29，运行状态为 `waiting_user`，阶段状态为 `generated`。原成功结果只有嵌套的 `run` 与 `session`，中央写入回执不保留这两个完整对象，模型实际收到 `status=ok`、`data={}`。模型随后误称任务仅启动、结果尚未产出。

## 当前实现

- 运行时根据冻结输入中的阶段资料是否为空，确定结构字段 `initialize_stage`；首次实体生成必须同时返回完整阶段字段。首版合并保留这些字段，既有阶段的单实体新增或修订继续保留原阶段元数据和无关实体。该边界不解析用户自然语言，也不自动选择另一个工具或目标。
- 必需的主线文本字段纳入共享契约，缺少字段时进入同一模型的一次结构修复；仍不符合契约则返回 `creation_generated_stage_fields_missing` 和具体 JSON 路径，并持久化为 `invalid_model_output`，不再丢失成无细节错误。
- 阶段结果在原有完整 API 返回旁提供统一的少量回执字段：真实 revision、阶段状态、保存标志、是否待确认、实体集合数量及运行 ID。模型投影保留这些事实，完整正文仍通过读取工具获取。
- 收尾提示明确区分“已保存、待作者确认”和“已启动、尚未生成”，要求以最新写入 revision 为准。没有通过关键词或正则判断、重写模型对用户意图的理解。
- Android 从 PC 导出阶段字段、初始化说明和写入回执契约，独立实现同一保存边界。手机回执同样包含保存状态、确认状态、revision 和实际集合数量，不依赖 PC 客户端运行。
