## 发现、修复与复测记录

### REL-001：打包 MCP 从外部工作目录误读 Hermes `.env`

- 严重度：阻断。
- 现象：从 Hermes Agent 等外部程序启动 `Siming.exe --mcp-server` 时，Pydantic 对 `TERMINAL_TIMEOUT`、`BROWSERBASE_PROXIES` 等 11 个 Hermes 字段报 `extra_forbidden`，MCP 尚未初始化就退出。
- 根因：`env_file=".env"` 是相对当前工作目录解析；打包 MCP 继承了调用方 CWD，因而把 Hermes 的 `.env` 当成司命配置。这是 CWD configuration leakage，不是“旧版司命 `.env` 残留”。只加 `extra="ignore"` 仍可能静默吞入同名合法字段，不能解决跨程序污染。
- 修复：源码开发模式继续允许项目 `.env` 并以 `extra="ignore"` 兼容旧字段；PyInstaller 冻结态一律用 `Settings(_env_file=None)`，只接受真实环境变量。同时打包版 MCP 配置写入司命自己的应用目录作为 `cwd`，形成第二道边界。
- 防复发：打包冒烟测试创建带截图中 11 个 Hermes 字段、以及一个故意无效的司命同名字段的 `foreign-agent/.env`，从该目录启动真实 `Siming.exe --mcp-server`，要求 `initialize`、`tools/list` 和写入链路均成功。
- 复测：源码设置回归与真实打包 MCP 异目录冒烟均通过。

### REL-002：CLI 配置器中途异常后可能没有可还原记录

- 严重度：高。
- 现象：第三方配置写入器若在改完部分文件后抛异常，接口返回失败，但用户可能无法从同一入口恢复原文件。
- 根因：只在“配置成功”路径保存回滚快照。
- 修复：无论配置器最终成功还是异常，只要检测到文件发生变化，就保存加密的动作前快照并开放“还原”。
- 防复发：新增“写入后抛异常仍可完整还原”测试。
- 复测：通过。

### REL-003：多文件还原中途失败可能留下新旧混合状态

- 严重度：高。
- 现象：还原第二个文件失败时，第一个文件已回到旧版本，CLI 处于不可预测的混合配置。
- 根因：还原动作缺少失败补偿。
- 修复：还原前记录本次动作前状态；任一文件失败时，把已经处理过的文件补偿回“点击还原之前”的状态，并保留再次还原能力。
- 防复发：新增两文件还原故障注入测试。
- 复测：通过，19 个 CLI 配置相关测试全部通过。

### UX-004：立项资料确认后，聊天或卡片仍可能显示“待确认”

### REL-006：本地模型把“最大上下文”误当成“推荐启动上下文”

- 严重度：高。
- 现象：16GB 显存、32GB 内存的标准档设备被推荐以 262K 上下文启动模型；模型中心也会把模型最大能力 262K 直接作为默认启动值。这会显著放大 KV Cache，容易出现显存/内存不足、长时间加载后失败和反复重试。
- 根因：模型能力上限与设备安全默认值共用了同一字段；运行时默认选择模型上限而非硬件建议。
- 修复：保留模型 262K 能力上限，但把轻量/标准/高质量设备的安全启动建议分别改为 8K/16K/32K；默认启动值取“模型上限与硬件建议中的较小值”。GPU 加载失败时，在不缩短上下文的前提下自动回退到 CPU/系统内存。
- 防复发：新增三档硬件建议、默认上下文上限和 GPU→CPU 同上下文回退测试。
- 复测：运行时安装成功；27B Q4 模型在 16K 上下文下首次约 27 秒、文件缓存后约 12 秒加载成功；英文与中文最小回答均成功。100 次经应用模型网关的连续真实回答全部成功，详见下方样本统计。

### ENV-007：当前安装的 CLI 并不等于当前可用模型

- 严重度：环境风险（应用需正确隔离，不应让用户踩坑）。
- 真实最小调用结果：7 个已安装 CLI 中，Claude 返回额度不足；MiMo 返回 API Key 无效；Kilo 要求登录；OpenClaw 缺少提供商密钥；Codex 在 90 秒内未完成；Qwen 退出并给出无沙箱警告；OpenCode 完成调用。
- 结论：只按“命令存在”展示为可用会造成高失败率。当前模型选择器只接受 `ready` 且真实对话通过的配置，这一防线需要继续通过端到端流程验证。
- 后续：分别复测可用 CLI 的中文/英文提示、输出解析、超时与错误分类，并确保失败配置不会成为默认模型。

### REL-008：运行时大文件遇到一次断流就失败，且失败任务从模型中心消失

- 严重度：高。
- 真实复现：llama.cpp 运行时首个归档下载至约 145MB 时远端断流；手动点击续传后首个归档完成，但 CUDA 依赖归档又在约 161MB 处断流并再次失败。
- 根因：单个下载源每轮只尝试一次；虽然底层保留 `.part` 文件，但必须由用户手动续传。模型中心又过滤掉 `failed` 任务，用户在被告知“返回模型中心”后看不到续传入口。
- 修复：对连接中断、超时、408/425/429 和 5xx 自动进行最多 3 次指数退避续传，继续使用已保存字节；磁盘不足和 4xx 永久错误不盲目重试。模型中心保留失败任务、展示错误原因，并提供“重试并续传”。
- 防复发：新增真实字节偏移续传测试，以及可重试/不可重试错误分类测试。
- 补充修复：多归档安装的后续依赖失败后，重试会直接复用已原子完成的主归档，不再重新下载 250MB 主包；若配置了 SHA256，则复用前仍会校验，损坏文件会重新下载。
- 复测：真实任务从 CUDA 依赖的 163,577,856 字节断点继续至 391,443,627 字节并完成安装；主归档未重复下载。相关下载、生命周期与本地模型测试共 23 项通过。

### REL-009：Windows 无害连接关闭竞态被记录成整屏系统异常

- 严重度：中高（可用性与可诊断性）。
- 现象：服务实际健康，但启动日志出现 `_ProactorBasePipeTransport._call_connection_lost` 与 `WinError 10054` 堆栈，和用户截图中的阻断错误外观相同，容易让用户误判应用已崩溃，也会淹没真正异常。
- 根因：Windows Proactor 在对端刚好先关闭连接时，将传输层清理竞态交给默认事件循环异常处理器。
- 修复：只过滤“Windows + 10054 + `_call_connection_lost`”这一精确组合；其他事件继续交给原处理器或默认处理器。
- 防复发：新增平台、错误码、回调名称三重匹配及真实异常委托测试。
- 复测：重启、健康检查和连续模型调用后日志保持干净，其他异常委托测试通过。

### REL-010：本地模型已可用，但目录接口同时显示 `stopped` 与 `running=true`

- 严重度：高。
- 真实复现：27B 模型已监听端口且 `/health` 正常，模型中心目录接口却同时返回持久化状态 `stopped` 和实时状态 `running=true`。
- 根因：启动请求的客户端提前断开时，持久化状态可能滞后；复用已有健康进程的快速路径没有主动校准数据库状态，目录接口也没有明确实时健康事实源。
- 修复：复用健康进程前重新写入运行状态；目录接口以实时健康为运行事实来源，持久化状态用于非运行阶段。
- 防复发：新增“健康运行时复用前校准状态”测试。
- 复测：重新加载后目录接口统一返回 `status=running` 与 `running=true`；应用内回答成功。

### SEC-011：本地 llama.cpp 默认允许任意网页跨域调用且没有鉴权

- 严重度：高（本机资源滥用与隐私风险）。
- 真实证据：旧运行日志明确提示 CORS 为 `*`、无 API Key，并标注存在跨域攻击风险。即使只绑定 `127.0.0.1`，用户访问的恶意网页仍可能尝试调用本机服务。
- 修复：每次启动生成新的高熵随机 API Key，仅保存在后端进程内；模型适配器在调用前取当前进程密钥；llama.cpp CORS 限制为 `localhost`；诊断命令把密钥替换为 `<redacted>`。
- 验证：无密钥聊天请求返回 401；来自 `https://evil.example` 的预检响应不包含 `Access-Control-Allow-Origin`；应用内带动态密钥的真实回答成功；日志中没有明文密钥。

### REL-012：首个本地模型已经运行，助手仍提示“还差一步”

- 严重度：高。
- 真实复现：隔离 QA 数据库中注册并成功启动首个 GGUF 后，模型中心显示运行正常，但 AI 助手没有可用的全局默认配置，继续把用户引导到配置流程。

- 修复：手动验证和本地模型启动共用“仅在没有健康默认模型时晋升”的规则；首次可用模型自动成为默认模型，但绝不覆盖用户已有的健康选择。接口显式返回 `became_global_default` 供界面反馈。
- 防复发：新增首次晋升、已有默认不覆盖及配置验证回归测试。
- 复测：本地模型重载后，助手顶部模型状态显示 `local_llama_cpp`，原“还差一步”提示消失；相关本地模型与配置测试 104 项通过。

### UX-013：完整编辑器在窗口缩窄时突然消失

### UX-014：作者直接编辑已确认资料后，状态被降级为“待确认”

### UX-015：自动任务列表缺少可发现、可防误触的删除入口

### REL-025：并发创建系统对话会触发 SQLite `database is locked` 并返回 500

- 严重度：阻断（并发用户/重复点击）。
- 真实复现：30 并发写入下出现真实 `sqlite3.OperationalError: database is locked` 与 HTTP 500。
- 根因：异步路由直接在事件循环线程调用同步 SQLAlchemy `flush()`；第一个请求等待依赖收尾提交时，第二个请求在 SQLite 忙等待中阻塞事件循环，使第一个事务无法及时释放锁。
- 修复：系统对话存储操作移入 Starlette 线程池，让事件循环可以继续完成事务提交与依赖收尾。
- 防复发：新增临时文件 SQLite + ASGI 并发回归；修复前可稳定得到多个 500，修复后 12/12 成功并全部持久化。
- 复测：真实服务连续完成 100 个“创建对话 → 开始回合 → 写入结果 → 读取 → 删除”生命周期，共 600 请求全部 200；P50 3.12ms、P95 427.5ms、最大 3659.94ms。

### SEC-033：用户在聊天中给出本地路径时，CLI 缺少可知情授权的安全读取通道

- 严重度：高。
- 风险：完全禁止会让用户无法交付本地参考资料；把路径文字直接视为许可，或向 CLI 开放原目录，则会把父目录、相邻文件、凭据和提示词注入一起带入权限面。
- 修复：仅为 OpenCode 增加独立的“读取一次”确认。发送路径后先列出精确目标，用户确认后后端才解析真实路径，并把受支持内容复制到每回合隔离目录的只读快照；CLI 只收到快照清单，不获得原路径、父目录、相邻文件、Shell、写文件或额外 MCP 权限。读取授权与结构化数据写入/MCP 授权分别确认，回合结束后先解除 Windows 只读属性，再整体删除隔离目录；清理函数只接受系统临时目录下带司命固定前缀的直属目录。
- 安全边界：拒绝相对路径、UNC/设备路径、磁盘根目录、用户主目录、Windows 目录、凭据/密钥文件、隐藏敏感目录以及任一层符号链接或 Junction；目录最多 80 个文件、24 MB、5 层，单文件最多 8 MB；DOCX 额外限制压缩包条目数、解压体积和提取文本体积。普通文件内容按不受信任数据处理，不能覆盖 SYSTEM/USER 指令。
- 兼容策略：目前只对能够稳定使用隔离工作区和进程级权限配置的 OpenCode 开放；其他 CLI 在有同等级沙箱证据前不会复用这条路径通道。
- 防复发：覆盖路径提取、显式确认、路径归一化、敏感文件、父级链接、DOCX 解压膨胀、快照范围、只读文件清理、OpenCode 全局配置隔离以及读/MCP/写三类授权互不提升。

## 尚未解决/待验证

- llama.cpp 原始请求在客户端取消时，底层生成槽位可能继续工作到本轮最大输出后才释放；这不影响上述资格准确性，但会拖慢紧随其后的请求。需要后续把 HTTP/SSE 取消信号继续传播到本地运行时。
- Xiaoyu 的外部账户当前余额/额度不足；司命现已正确显示并终止重试，但应用无法代替用户补充第三方额度。正式数据库在本轮只读探测中未被改写，用户可在设置页点击“重新验证”让状态按当前结果持久更新。
- React 开发模式会记录 React Router 未来版本提示与 Ant Design `findDOMNode` 弃用警告；它们未造成当前用户操作失败，但会污染错误日志，需要在可靠性清理阶段分类处理。
- 仓库级 Ruff 仍会报告大量既有格式与现代化规则债务；本轮实际修改的后端文件均通过 Ruff，完整运行测试通过。该静态债务未冒充本轮运行时缺陷，也未做跨范围机械重写。
- Vite 仍提示可视化页与主入口存在大于 500KB 的构建分包；当前加载和交互验收通过，但后续可按路由进一步拆包。
- 重复样本只覆盖当前硬件、短回答和单并发；长文本、多并发、供应商维护窗口与其他设备仍需持续监测，不能由本轮样本推导为普遍保证。
